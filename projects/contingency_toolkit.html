Background

From study to tool

The first four projects in this portfolio are studies: each asks a question, answers it, and stops. This one is different. It is a tool — a reusable ContingencyAnalyzer class that takes any pandapower network, screens every single-line outage, and reports violations, either sequentially or across worker processes.

N-1 security is the underlying requirement in both major reliability frameworks. In Europe the (N-1) criterion is defined in Commission Regulation (EU) 2017/1485, Article 3. In North America the planning equivalent is NERC TPL-001. Screening is the routine operation that checks it, and on a large network it is run constantly.

N-1 screening is also embarrassingly parallel: every contingency is independent of every other, so nothing needs to be shared between them. The obvious question is how much speed-up that actually delivers — and the honest version of that question requires proving the parallel path returns exactly the same answers as the sequential one before quoting any timing at all.

Honesty, up front

The modelling assumption that drives every violation count

The line ratings in the IEEE 118-bus case are invented. The University of Washington archive is explicit that the MVA limits were not part of the original 1962 AEP data. With pandapower’s defaults, the base case peaks at 4.5 percent loading, so nothing ever violates and screening is pointless.

I derive ratings as 1.3× the base-case current with a floor, which puts the base case at 76.92 percent. Every violation count below depends on that choice. The timing results, which are the actual subject of the project, do not.

Stating this before the results rather than in a footnote is deliberate. A reader who takes “129 of 173 contingencies violate” as a property of the IEEE 118-bus network would be misled; it is a property of my ratings assumption applied to that network.

Methodology

What the class does

ContingencyAnalyzer takes a network and, for each of the 173 lines: removes it from service, re-solves AC power flow by Newton-Raphson, records the maximum line loading, the voltage extremes and the violation counts, then restores the line and moves on. It exposes a single entry point:

Usage
  • from src.contingency import ContingencyAnalyzer, build_net
  • results, runtime = ContingencyAnalyzer(build_net()).screen(parallel=True, workers=4)
  • results.sort_values("max_loading", ascending=False).head()

The parallel path uses concurrent.futures.ProcessPoolExecutor. Before any timing is reported, the sequential and parallel result frames are compared element by element and must be identical.

Key finding

2.85× speed-up on 4 cores — a 64.9 percent runtime reduction — with results verified identical to the sequential run.

Scaling is sub-linear: 2.85× where the ideal would be 4×. Process startup, pickling the network out to each worker and collecting results back are fixed costs that do not shrink as cores are added, and on a problem this small they are a visible fraction of the total. The gap between 2.85 and 4 is the interesting part, not the speed-up itself.

Two implementation details that were necessary, and neither is obvious

  • The worker function must be defined at module level. ProcessPoolExecutor pickles the callable to send it to a subprocess, and a bound method or a closure fails with a pickling error that does not point anywhere near the actual cause. This costs an hour if you have not hit it before.
  • The network is passed once per worker through an initialiser, not once per task. Sending a copy of the network with each of the 173 tasks costs more in serialisation than the power flow costs to solve — the parallel version can end up slower than the sequential one. This is the difference between parallelism that works and parallelism that looks like it should.
The larger point about optimisation: production contingency tools do not get their speed from parallelism. They run a fast DC pre-screen and only solve full AC for the marginal cases, which is a far larger saving than throwing cores at the problem. Parallelism is the easy win; algorithmic selection is the real one.

Honesty

Limitations

  • Line outages only. Generator and transformer contingencies are the obvious extension and the class is structured to take them.
  • AC power flow for every case, as noted above. The DC pre-screen is the bigger optimisation and is not implemented here.
  • Derived thermal ratings. Every violation count is conditional on the 1.3× assumption stated at the top of this page.
  • Only four cores. The interesting scaling questions begin at 32 or more, where communication cost and memory bandwidth start to dominate differently.
  • No N-1-1 or common-mode outages, which is where real transmission planning spends much of its effort.
